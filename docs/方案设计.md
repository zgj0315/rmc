# Remote Maintenance Client 方案设计

## 1. 场景与目标

客户现场一体机部署在私有网络中，**无法访问互联网**。现场工程师使用 Windows 笔记本，可同时访问客户内网中的一体机和互联网。

目标：公司远程工程师通过现场 Windows 笔记本安全地 SSH 登录一体机进行运维，同时满足：

- 不改变客户网络结构，不开放客户侧入站端口，不在笔记本上启用 NAT、ICS 或网段转发；
- 只暴露一体机的 SSH 端口，不暴露客户网络中的任何其他地址；
- 所有连接由现场笔记本主动发起，由现场人员明确开启、可随时关闭、能看到谁在连接；
- 一体机不改镜像、不装 agent，方案对已交付设备零改动。

### 非目标

- 不做子网路由或 VPN 接入；
- 不在一体机上部署常驻 agent，不修改一体机镜像；
- V1 不做 Gateway 侧会话录制（原因见第 8 节），不做客户端自动更新；
- 不做专门的文件传输功能，scp 与 sftp 天然走隧道。

## 2. 总体架构

```
公司远程工程师
      │  ssh -J，输入一体机动态 root 口令
      ▼
┌──────────────────────────────────────────────────┐
│ Maintenance Gateway   gateway.company.com        │
│                                                  │
│  :22   sshd-engineer   工程师入口，无 shell，仅跳转 │
│  :443  haproxy TLS 终止 ──► 127.0.0.1:2222       │
│                              sshd-tunnel         │
│                              仅 tunnel-* 用户     │
│                              反向端口 127.0.0.1:22001… │
└────────────────────────▲─────────────────────────┘
                         │ TLS 1.3
                         │   └─ SSH，russh，口令认证，反向端口转发
                         │ 笔记本主动发起，可经 HTTP CONNECT 代理
                     Internet
                         │
┌────────────────────────┴─────────────────────────┐
│ Windows 笔记本    Remote Maintenance Client       │
│   iced UI ◄── 事件 ── rmc-core（内嵌 russh）      │
└────────────────────────┬─────────────────────────┘
                         │ TCP 192.168.100.10:22，本次会话唯一目标
                         ▼
┌──────────────────────────────────────────────────┐
│ 客户一体机   sshd   现状不变，root 动态口令登录     │
└──────────────────────────────────────────────────┘
```

两段认证相互独立：

1. **笔记本到 Gateway**：现场人员在客户端界面输入 Gateway 上的隧道账号与密码，Gateway 地址同样可现场编辑。该账号是 Gateway 的低权限系统账号，shell 为 nologin，只能创建一个指定的 loopback 反向端口，不能开 shell、不能转发到别处。
2. **工程师到一体机**：工程师登录 Gateway 跳转端口后，输入一体机 root 动态口令。口令由公司内部服务按设备编号计算得出，逐台不同、可轮换。这一段是端到端加密穿过隧道的，Gateway 看不到口令。

即使 Gateway 被完全攻陷，攻击者能到达的也只有一体机的 SSH 端口，仍需要一体机的动态 root 口令才能登录。

## 3. 客户端设计

### 3.1 技术选型

| 项目 | 选择 | 理由 |
|---|---|---|
| 语言与运行时 | Rust，tokio | 核心逻辑跨平台可测 |
| SSH | russh，锁定版本 | 只用到连接、host key 校验、口令认证、tcpip-forward、forwarded-tcpip 五个能力；口令在界面输入，用回调直接送入，无需子进程；每个远程会话都是回调，可见可控 |
| TLS | rustls + webpki-roots | 根证书内置，不受 Windows 证书库中企业注入根影响；Gateway 使用公共 CA 证书 |
| GUI | iced | 纯 Rust；wgpu 不可用时回落到 tiny-skia 软件渲染，能在 RDP、虚拟机、无独显驱动机器上运行 |
| 托盘 | tray-icon crate | 最小化到托盘并用颜色表示状态 |

不采用驱动 `ssh.exe` 子进程的方案：BatchMode 会禁用口令认证，Windows 上无 sshpass，GUI 程序无法把界面输入的口令可靠喂给子进程。内嵌 russh 则是一次认证回调。

### 3.2 crate 划分

```
rmc/
├── crates/
│   ├── rmc-core    平台无关：配置、传输层、SSH 隧道、状态机、重连、会话账目、审计
│   ├── rmc-win     Windows 适配：系统代理与 SSPI 代理认证、电源与网络事件、单实例、托盘、通知、DPAPI
│   └── rmc-app     iced 界面
├── gateway/        Gateway 部署文件与运维脚本
└── docs/
```

rmc-core 不依赖 Windows API，在 Linux 上做集成测试；rmc-win 的平台能力以 trait 注入 core。

### 3.3 核心组件

| 组件 | 职责 |
|---|---|
| Config | known_hosts 与允许端口；现场可编辑的 Gateway 地址与一体机地址 |
| Transport | 建立到 Gateway 的字节流：TCP，可选 HTTP CONNECT（407 时委托平台层做 SSPI 协商），TLS |
| SshTunnel | 在字节流上运行 russh：校验 host key、口令认证、请求反向端口、处理每条转发连接 |
| Supervisor | 状态机、预检、重连、远程会话账目 |
| Preflight | 一体机 :22 可达、Gateway DNS/TCP/TLS 可达、代理探测 |
| Audit | 本地追加式日志：状态变迁、每个远程会话起止与流量 |

core 对外只暴露 `TunnelEvent`、`Command`、`Supervisor::spawn`。凭据通过 `Command::Start { username, password, gateway_addr, appliance_addr }` 一次性传入，仅存于内存，认证后即清除。

### 3.4 隧道建立流程

```
现场人员输入隧道账号与密码，确认 Gateway 与一体机地址，点击"开启远程维护"
   │
   ▼
Preflight
   ├─ TCP 连接 一体机:22，读取 host key 指纹
   ├─ 解析 Gateway 域名，TCP 连接 :443（经代理时用 CONNECT，遇 407 用 SSPI 协商）
   └─ TLS 握手，校验证书链与 SNI
   │
   ▼
SshTunnel
   ├─ SSH 握手，校验服务端 host key，首次连接记录，之后变更即拒绝
   ├─ 口令认证，提交隧道账号与密码
   ├─ 发送 tcpip-forward 127.0.0.1:22001，等待 REQUEST_SUCCESS
   └─ 进入 Connected，每 10 秒 keepalive，3 次无应答判定断线
   │
   ▼
每当 Gateway 打开 forwarded-tcpip 通道
   ├─ 校验监听端口为已注册端口
   ├─ TCP 连接一体机:22，双向转发
   └─ 上报 RemoteSessionOpened / RemoteSessionClosed
```

转发目标是本次会话开启时确认的唯一地址，会话期间不可更改，远程侧无法更改。

### 3.5 状态机

```
Idle ──开启──► Preflight ──通过──► Connecting ──forward 成功──► Connected
                  │                    │                           │
                失败              致命错误                链路断开 / keepalive 超时
                  ▼                    ▼                           ▼
               Failed               Failed              Backoff(n) ──定时器或网络事件──► Connecting
                                                               │
Connected ──一体机探测失败──► Connected{degraded}          端口占用重试超时 ──► Failed
Connected ──用户停止或客户端退出──► Stopping ──► Idle
```

| 状态 | 界面 | 允许操作 |
|---|---|---|
| Idle | 灰色，一体机地址、Gateway 地址与账号口令可编辑 | 开启 |
| Preflight / Connecting | 蓝色，当前步骤与进度 | 取消 |
| Connected | 绿色，会话计时与远程会话列表 | 停止，断开某个远程会话 |
| Connected{degraded} | 橙色，"隧道正常，一体机不可达" | 停止 |
| Backoff(n) | 黄色，"第 n 次重连，x 秒后" | 停止，立即重试 |
| Failed | 红色，原因与建议 | 重试，查看诊断 |

### 3.6 错误分类与重连

| 类别 | 示例 | 处理 |
|---|---|---|
| 致命 | host key 不匹配、TLS 证书链无效 | 立即 Failed，不重试，界面醒目提示 |
| 认证失败 | 账号或密码错误 | 停止并回到 Idle，提示重新输入，不自动重试 |
| 端口占用 | tcpip-forward 被拒，上次僵尸监听未回收 | 固定 5 秒重试，最长 120 秒，超时 Failed |
| 网络类 | DNS/TCP/TLS/keepalive 失败 | 退避 1、2、5、10、20、30 秒封顶，附加 ±20% 抖动 |
| 一体机不可达 | 转发连接一体机:22 失败 | 隧道保持，转 degraded，每 30 秒探测，恢复后转回 |

链路断开后重连时若原会话已通过认证，凭据仍在内存，可直接复用，无需再次输入。收到 Windows 网络变化或休眠恢复事件时清零退避并立即重连。认证失败不自动重试，防止触发 Gateway 登录限速与账号锁定。

### 3.7 远程会话可见性

- 界面显示本次隧道的已连接时长；
- 每个远程会话单独列出起止、时长、流量，现场人员可单独断开；
- 远程会话打开与关闭时发送系统通知。

会话时长上限与空闲自动停止不在 V1 范围，见 7.3。隧道在现场人员手动停止或客户端退出前保持连接。

### 3.8 凭据与存储

- 目录 `%LOCALAPPDATA%\rmc\`；
- Gateway 隧道账号与密码由现场人员每次开启时在界面输入，仅存于进程内存，认证后清除；**默认不保存密码**；
- 若开启"记住密码"，用 DPAPI 当前用户范围加密后落盘；
- Gateway host key 首次连接时记录到应用目录下的 known_hosts，之后变更即拒绝连接并告警；V1 不内置固定列表，见 7.3；
- 允许端口编译进客户端二进制；
- Gateway 地址与端口、一体机地址与端口可现场修改，默认值内置，本地存储；
- 日志按天滚动保留 30 天，不记录口令与转发内容。

### 3.9 Windows 集成

- 单实例：命名互斥量，第二个实例置前已有窗口；
- 电源事件：休眠恢复后立即触发重连；
- 网络事件：连通性变化后立即触发重连；
- 系统代理：读取 WinHTTP/IE 代理配置，存在 PAC 时对 Gateway 域名求值；
- 代理认证：代理对 CONNECT 返回 407 时，用 SSPI 协商 Negotiate 与 NTLM，直接复用当前登录用户的 Windows 身份，现场人员不需要输入代理凭据。协商失败时在诊断页明确报告代理要求认证，而不是笼统的连接超时；
- 不需要管理员权限，安装为按用户目录的便携包；
- 可执行文件做 Authenticode 签名，避免 SmartScreen 拦截。

## 4. Gateway 设计

V1 不开发服务端程序，由 haproxy 与两个独立 sshd 实例组成。

### 4.1 拓扑

```
:443  haproxy   TLS 终止，公共 CA 证书 ──► 127.0.0.1:2222  sshd-tunnel
:22   sshd-engineer   工程师入口
```

互联网暴露面只有 haproxy 与工程师入口，两个 sshd 配置独立。

### 4.2 sshd-tunnel

```
# /etc/ssh/sshd_tunnel_config      systemd: sshd-tunnel.service
ListenAddress 127.0.0.1:2222
UsePAM yes
AuthenticationMethods password
PasswordAuthentication yes
PubkeyAuthentication no
AllowUsers tunnel-*
ClientAliveInterval 10
ClientAliveCountMax 3
LoginGraceTime 20
MaxAuthTries 3
GatewayPorts no
AllowTcpForwarding remote
PermitOpen none
PermitTTY no
X11Forwarding no
AllowAgentForwarding no
AllowStreamLocalForwarding no
ForceCommand /bin/false
Match User tunnel-zhang
    PermitListen 127.0.0.1:22001
```

- 每个隧道账号一个系统用户，shell 为 nologin；
- 认证走 PAM 口令认证，口令存放于隧道专用口令库，不使用域账号；
- 端口限制写在 `Match User` 块的 PermitListen 中；
- `GatewayPorts no` 在服务端强制反向端口只绑定 loopback，不依赖客户端传入的地址；
- ClientAlive 保证客户端异常断线后 30 秒内回收反向端口，配合客户端端口占用重试，异常恢复时间在 30 到 60 秒。

haproxy 片段做 TLS 终止与每 IP 连接限速：

```
frontend tunnel_in
    bind :443 ssl crt /etc/haproxy/certs/gateway.pem
    mode tcp
    default_backend sshd_tunnel

backend sshd_tunnel
    mode tcp
    server local 127.0.0.1:2222
```

sshd 日志来源均为 127.0.0.1，真实来源 IP 以 haproxy 日志为准。

### 4.3 sshd-engineer

工程师在 Gateway 无 shell，只能跳转到 loopback 隧道端口：

```
# /etc/ssh/sshd_config.d/engineer.conf
PasswordAuthentication no
Match Group engineers
    AllowTcpForwarding local
    PermitOpen 127.0.0.1:*
    PermitTTY no
    ForceCommand /bin/false
```

工程师登录一体机（口令为该设备的动态 root 口令）：

```
ssh -J eng@gateway.company.com -p 22001 \
    -o HostKeyAlias=c0001-a1 \
    root@127.0.0.1
```

`HostKeyAlias` 按设备编号记录一体机 host key，避免不同一体机复用同一端口时的 host key 变更告警；设备指纹在登记表中留存一份，供核对。

### 4.4 登记表与脚本

`gateway/registry.toml` 为唯一事实来源：

```toml
[[tunnel_account]]
username   = "tunnel-zhang"
owner      = "张三"
port       = 22001
appliances = ["c0001-a1"]
```

脚本：

- `enroll-account.sh`：创建系统用户、写 `Match User` 块、生成并下发初始密码；
- `revoke-account.sh`：禁用账号并踢掉在线连接；
- `tunnel-status.sh`：汇总当前在线反向端口及对应账号。

工程师账号在 sshd-engineer 上单独管理。

## 5. 一体机侧

**一体机不做任何改动。** root 采用动态或高强度口令，由公司内部服务按设备编号计算得出，逐台不同、可轮换。工程师维护时从内部服务取当台设备的当前口令，在 SSH 提示符输入。口令仅在工程师到一体机的端到端加密通道中传输，Gateway 不可见。

---

## 6. 身份与端口

- 隧道账号绑定人（现场工程师），不绑定笔记本，客户端二进制统一，无需逐台注册；
- 反向端口按隧道账号分配并登记，V1 每账号一个端口，一次维护一台一体机；`appliances` 为列表，为多台预留；
- 新增：管理员在 registry 增记录，运行 enroll 脚本得到账号与初始密码，交付现场人员，首次连接后由现场人员改密；
- 吊销：运行 revoke 脚本禁用账号，在线连接被踢掉。

## 7. 安全设计

### 7.1 威胁模型

| 攻击者 | 能拿到 | 拿不到 | 控制措施 |
|---|---|---|---|
| 被盗或被入侵的笔记本 | 若开启记住密码则得隧道口令，可建立隧道 | Gateway shell、其他端口、一体机登录 | 默认不存密码，存则 DPAPI 绑定 Windows 账号；PermitListen 限端口；账号可吊销 |
| 钓鱼 / 假 Gateway | 现场人员的隧道口令 | 一体机登录，仍需动态 root 口令 | V1 只有 host key 首次记录与变更拒绝，固定列表见 7.3 |
| 被完全攻陷的 Gateway | 通过在线隧道到达一体机 :22 | 一体机 root 口令（端到端加密，Gateway 不可见） | 口令由内部服务计算，逐台不同、可轮换；haproxy 与 sshd 最小配置 |
| 越权 / 恶意工程师 | 取到口令即可登录对应在线一体机 | 客户网络其他地址 | 两跳均有 sshd 日志；口令按设备隔离并轮换；V2 引入取口令审批与 RBAC |
| 客户内网攻击者 | 观察到笔记本到一体机的 SSH 连接 | Gateway 端口、隧道内容 | 笔记本不监听任何入站端口 |

最重要的性质：即使 Gateway 被完全攻陷，攻击者能到达的也只有一体机 SSH 端口，仍需一体机动态 root 口令。

### 7.2 最小权限清单

- 一体机始终不能访问互联网；
- Windows 不开启 NAT、ICS 或网段转发，客户端不监听任何入站端口；
- 客户端只把 Gateway 打开的通道转发到本次会话确认的唯一一体机地址；
- Gateway 反向端口只监听 127.0.0.1，由 `GatewayPorts no` 服务端强制；
- 笔记本到 Gateway 使用 Gateway 专用低权限口令，host key 变更即拒绝连接；
- 工程师在 Gateway 无 shell，一体机 root 口令动态且逐台隔离；
- 远程维护默认关闭，由现场人员开启，每个远程会话可见可断，可随时停止；
- 客户端退出、崩溃或被强杀时隧道随进程消亡，无残留。

### 7.3 后续加固（V1 不做）

V1 以打通功能为先，下列措施排在功能之后，每一项都不改动整体架构：

- 固定 Gateway host key 列表并取消首次连接信任，防止假 Gateway 收集隧道口令；
- Gateway 的 PAM 栈加入第二因素，客户端只多一个输入框；
- pam_faillock 失败锁定与 haproxy 按来源 IP 限速；
- 会话时长上限与空闲无远程会话自动停止，参数可现场调小；
- 记住密码从 DPAPI 升级为绑定设备的凭据保护；
- 工程师侧引入 bastion 做集中授权与会话录制，见第 10 节。

- 用例：正常建链与转发；密码错误后停止且不自动重试；host key 变更时拒绝连接并告警；Gateway 断开后按网络类退避重连；SIGSTOP 冻结 sshd 模拟僵尸端口验证端口占用重试；host key 不匹配立即 Failed；一体机 sshd 停止转 degraded 并恢复后转回；HTTP CONNECT 代理路径；代理返回 407 后走 SSPI 协商，协商失败时报出代理认证错误；断线重连复用内存中凭据；

## 10. 演进路线

- **bastion**：候选 Warpgate，Rust 实现，自带 Web 管理、OIDC 单点登录、TOTP、角色到目标授权、SSH 会话录制回放。每个反向端口配为一个 target，工程师经 bastion 登录，由 bastion 在连接时向内部口令服务取一体机口令，工程师不再直接接触 root 口令。代价是 bastion 终止 SSH 后再连一体机，牺牲端到端加密换取录制与集中吊销，需在 V2 立项时明确取舍。
- **设备登记服务**：替代 registry 文件，提供动态端口分配、在线状态、维护审批、取口令审计。
- **多一体机并发维护**与**客户端自动更新**。

## 11. 已考虑但未采用的方案

| 方案 | 未采用原因 |
|---|---|
| 驱动 ssh.exe 子进程 | 与页面输入口令认证不兼容（BatchMode 禁用口令、无 sshpass）；还需 Job Object、私钥 ACL、stderr 解析、自写 ProxyCommand；无法感知单个远程会话 |
| 一体机内置证书 / CA | 需改镜像，且一体机长期离线时钟漂移导致证书校验失败；动态口令方案对已交付设备零改动 |
| frp 或 rathole | 认证不在 SSH 体系内，有历史 CVE，向客户安全团队解释成本高 |
| 覆盖网络：NetBird、Headscale、Tailscale | 需在接入客户内网的笔记本上装虚拟网卡与常驻服务，客户合规风险高 |
| GPUI | Windows 后端成熟度、软件渲染回落、托盘支持均未验证，对单窗口面板过重 |

---

## 12. 核心原则

> **客户网络不打通，只打通一体机 SSH 服务；所有连接由现场 Windows 主动发起并由现场人员控制；笔记本到 Gateway 用专用低权限口令，一体机用逐台隔离的动态 root 口令；Rust 内嵌 russh 管理隧道生命周期与安全策略，Gateway 与一体机不引入自研服务端。**
