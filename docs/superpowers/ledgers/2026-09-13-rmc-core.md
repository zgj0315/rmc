Ruling R1（F1 必改，影响 Task 1 与全局约束）：MSRV 1.82 不成立，抬到 1.89。
  实测：zeroize 1.9.0 是 edition 2024 / rust-version 1.85，cargo 1.82 连它的
  manifest 都解析不了；russh 0.63.3 是 edition 2024 / rust-version 1.89。
  计划解析出的 224 个包里有 84 个超过 1.82。
  两条路：抬 MSRV，或把 russh 钉在 0.54（最后一个 edition 2021 版本）并逐个
  封顶其余依赖。选前者——后者是一场大规模钉版本的苦工，且把整个客户端锁在
  一个 2024 年的 SSH 库上；本机工具链 1.95，这是给自家 Windows 客户端用的，
  1.82 本来就是随手定的数。rust-toolchain.toml、全局约束、Task 12 CI 里两处
  dtolnay/rust-toolchain@1.82 一并改成 1.89。
  错了的代价：构建本项目需要 Rust ≥1.89。

Ruling R2（F2 必改，影响 Task 7 与 Task 9）：russh 用 0.63，并按实测修四处。
  扫描者把计划的 handler.rs 原样对 0.63.3 编译，拿到四个各自独立致命的问题：
  一、`type Error = Error` 不满足 russh 要求的 `From<russh::Error>` 约束——这条
      与版本无关，0.54 同样要求。Task 1 的 Error 枚举必须加这个 From。
  二、impl 上的 `#[async_trait]` 是错的：0.5x 之后 Handler 用 AFIT
      （`-> impl Future`），而 async-trait 是 russh 的非默认 feature。去掉属性。
  三、`check_server_key` 收的是 `&PublicKeyOrCertificate` 而不是 `&PublicKey`，
      因此计划里算指纹的 `PublicKeyBase64::public_key_bytes` 用不上，必须先过
      `PublicKeyOrCertificate::public_key()`。指纹正是 Task 4 与方案 §3.10
      那个「复制」按钮的全部安全价值所在，这一处错不得。
  四、`server_channel_open_forwarded_tcpip` 多了一个 `reply: ChannelOpenHandle`
      参数，**而丢弃 reply 等于拒绝该通道**。计划的「接受」路径从不调用
      `reply.accept()`。只按编译报错补一个 `_reply` 就能编过，然后每一条被转发的
      通道都被静默拒绝、隧道什么都不转——这是编译器抓不到的功能性静默失败，
      是本次扫描最危险的一条。
  另外 russh 用 `default-features = false, features = ["ring"]`：默认走
  aws-lc-rs 会拖进 aws-lc-sys 的 C 构建（要 cmake，编译数分钟），计划的 20 分钟
  CI 超时没算这笔账。

Ruling R4（F5 + F6 必改，Task 9 与 Task 10）：状态机的 13 条测试现在跑的是
  真预检打真网络，而且不是失败而是**挂住**。
  F5：Command::Start 在 attempt 之前调 run_preflight，而 Deps 没有给预检留注入点；
      preflight::run 真的去 TcpStream::connect 和 lookup_host。测试里的地址
      （192.168.100.10:22 / gateway.company.com:443）不可达，于是预检返回 false、
      直接进 Failed，脚本化的假隧道一次都没被调用——计划自己在架构段落里
      宣称的「TunnelFactory 让状态机可以用假隧道纯单元测试」，在 Start 这条
      路径上并不成立。
  F6：supervisor 用 std::time::Instant 计时，而测试跑在 tokio 的
      `start_paused = true` 虚拟时钟上。虚拟时钟会瞬间跑到真实时钟前面很远，
      于是 `Instant::now() + delay` 转成一个**过去**的截止点，每次 sleep 立刻返回；
      反过来 PortBusy 分支里的 `since.elapsed()` 量的是真实时间，虚拟时间里恒为 0，
      那条 120 秒预算的测试永远到不了预算。
      两者叠加的结果是测试挂死而不是报错——又一次「失败路径没法报错」。
  改法：Task 9 交出一个 Preflight trait（或 Deps.preflight），Task 10 注入；
  supervisor 全程用 tokio::time::Instant。这两条要写进 Task 9 与 Task 10 的派发。

Ruling R14（来自 Task 1 审查的 Minor 1，现在就定，不留给 Task 10）：
  `Io(#[from] std::io::Error)` 一律归 Network 有问题：一个永远写不进去的
  known_hosts（权限不对、磁盘满）会被当成暂时性网络抖动，Supervisor 无限次
  拆了重建，而重连永远修不好它，工程师也等不到一个可处理的 Failed。
  但把 Io 整个改成 Fatal 更糟——blanket #[from] 意味着传输层 socket 上的任何
  io::Error 也会变成 Io，那会把一次暂时性的 socket 抖动直接判死。
  裁定：保留 `Io` → Network 作为安全的默认（socket 语义），另加一个
  `LocalIo` → Fatal，专用于本地文件系统操作。Task 4 的 known_hosts 读写必须用
  LocalIo——写不进 known_hosts 意味着记不下 host key，是安全相关、必须让人看见的。
  Task 11 的审计日志到时候自行判断，但先记一句：日志写不进去大概**不**该是 Fatal，
  把一次维护会话因为记不了日志而掐掉，代价对不上。
  这条随 Task 2 的派发一起落地（一个 match arm、一个变体、一条测试），
  不单开一轮修复。
