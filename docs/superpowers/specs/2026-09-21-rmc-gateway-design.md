# rmc-gateway：把运维服务器做成一个 Rust 二进制

日期：2026-09-21　状态：设计已口头确认，待过目

## 1. 为什么改

原方案（`docs/方案设计.md` 第 4 章）的运维服务器由 haproxy、一个隧道专用的 sshd 实例、
一个 systemd 单元、PAM 系统账号、`registry.toml`、一个 Python 脚本与三个 bash 脚本组成，
还要一张公共 CA 证书与一个域名。第一次真要部署时暴露出三件事：

- **部署路径从来没被跑过。** 测试环境在容器入口脚本里直接起 sshd 与 haproxy；
  README 里那串 `systemctl` 命令没有任何自动化验证，其中 `enable --now haproxy`
  对 Debian 上已经在跑的 haproxy 不起作用。
- **有一个没堵的口子。** 隧道账号是真实的系统用户，系统自带的 22 端口 sshd 默认
  也接受它们，而那一边没有任何转发限制——没有 shell 挡不住 `ssh -N -D`。
- **账号端口与客户端对不上。** 服务器按账号写死 `PermitListen <port>`，客户端却
  始终申请内置的 22000，界面上也没有填端口的地方。

用户的决定：**把运维服务器封装成一个 Rust 二进制**；**运维服务器没有域名，只用 IP**；
可以修改原方案，可以修改客户端。

这推翻了原方案第 12 节核心原则里「Gateway 不引入自研服务端」那一句。代价写在 §9。

## 2. 目标与非目标

**目标**：在一台干净的 x86_64 Linux 上，拷一个文件过去、`init`、`serve`、
放行防火墙（443 与 22000–22999），运维服务器就能工作。不装任何软件包，不要域名，
不要证书。

**非目标（这一轮不做）**：Web 管理界面；工程师一侧的认证、授权与会话录制；
口令自助修改；第二因素；一个账号同时维护多台一体机；多实例高可用；
x86_64 Linux 以外的发布物；与旧的 haproxy + sshd 服务端兼容。

## 3. 形态

新增 `crates/rmc-gateway`，lib + bin。

- **lib** 暴露一个可以在进程内启动的服务端（绑定地址、数据目录由调用方给，端口可以是 0），
  这是测试的入口，也是 bin 的全部内容。lib 必须在 Linux、macOS、Windows 上都能编译与
  运行——Windows CI 要用它跑客户端的端到端测试。
- **bin** 是一层薄 CLI。发布物是 `x86_64-unknown-linux-musl` 静态二进制，一个文件。

```
rmc-gateway init --public-addr 203.0.113.10:443
rmc-gateway serve [--listen 0.0.0.0:443] [--engineer-allow <CIDR>]...
rmc-gateway account add <name> [--port N] [--note <文字>]
rmc-gateway account passwd <name>
rmc-gateway account revoke <name>
rmc-gateway account list
rmc-gateway status
rmc-gateway fingerprint
rmc-gateway service install        # 仅 Linux：写一个 systemd 单元，可选
```

所有子命令都接受 `--data-dir`（环境变量 `RMC_GATEWAY_DATA`），默认 `/var/lib/rmc-gateway`。

### 3.1 数据目录

目录 `0700`，文件 `0600`。

| 文件 | 内容 |
|---|---|
| `identity.key` | ed25519 身份密钥。`init` 生成，已存在则拒绝覆盖 |
| `config.toml` | `public_addr`（只用于打印连接码）、端口区间（默认 22000–22999） |
| `accounts.toml` | 每个账号：名字、端口、口令的 argon2id 哈希（PHC 字符串）、是否启用、创建时间、备注 |
| `status.json` | `serve` 在状态变化时原子写出：在线隧道、端口、来源地址、各自的工程师连接 |
| `audit/audit-YYYY-MM-DD.log` | 审计日志，JSON Lines，保留 180 天 |

### 3.2 CLI 与服务进程之间没有 IPC

- CLI 改 `accounts.toml` 一律「写临时文件 → 属主设成数据目录的属主 → rename」，
  并用一个锁文件把并发的 CLI 调用串行化。
- 服务端在**每次认证**时读账号（按 mtime 缓存）。
- 服务端每个心跳周期（10 秒）复查每条在线隧道的账号是否还存在且启用，
  不是就立即拆掉——**吊销最迟 10 秒内踢掉在线会话**。
- `status` 读 `status.json`。服务进程不在跑时如实说「没有在跑」（按文件里的 pid 与
  更新时间判断），而不是打印一份过期的在线列表。

### 3.3 以什么身份运行

进程内**不写降权代码**（`setuid` 一类的调用是安全敏感的，而且要 `unsafe` 或新依赖）。

- 推荐：`service install`。它在缺少时创建系统用户 `rmc-gateway`，把数据目录属主改成它，
  写一个单元：`User=rmc-gateway`、`AmbientCapabilities=CAP_NET_BIND_SERVICE`、
  `NoNewPrivileges=yes`、`ProtectSystem=strict`、`ReadWritePaths=<数据目录>`、
  `Restart=on-failure`。进程**从头到尾不是 root**。
- 也允许直接 `sudo rmc-gateway serve`：能跑，启动时打印一条警告说明它正以 root 运行。

> 与口头确认的设计有一处不同：当时说的是「以 root 启动，绑定 443 之后降权到数据目录的
> 属主」。改成上面这样，是因为 systemd 能让进程**从一开始就不是 root**，比进程内降权
> 更强，还省掉一段安全敏感的代码。

## 4. 身份与连接码

### 4.1 一把密钥，一个指纹

`init` 生成一把 ed25519 身份密钥。

- TLS：用它自签一张 X.509 证书。证书在每次 `serve` 启动时现生成、只在内存里——
  客户端核对的是公钥，不是证书本身。
- SSH：同一把密钥就是 host key。
- **指纹 = 这把密钥 32 字节公钥的 SHA-256**，写成不带填充的 base64url（43 个字符）。

客户端在两层各核对一次**同一个**指纹：TLS 一侧取证书里的公钥，SSH 一侧取 host key 的
公钥。TLS 一侧**只**核对公钥并验证握手签名，不校验有效期、名称与证书链。

**只开 TLS 1.3。** 两端都是我们自己的，没有兼容包袱；而且 TLS 1.3 的证书是加密传输的，
路径上的被动检测设备看不到「签发者不受信任」。会失败的只有真的在做中间人的审计设备
——那正是应当失败的情形，客户端此时给出的处置建议与今天「证书不受信任」那一条相同
（请客户网管放行这个 IP 的 443）。

换密钥等于换身份：所有连接码作废，必须重新发放。运维手册里要写明备份数据目录。

### 4.2 连接码

```
rmc1:<账号>@<IP>:<端口>:<指纹>:<校验>
rmc1:tunnel-zhang@203.0.113.10:443:k3JxQm…（43 个字符）…:9f2c
```

- 账号：`[a-z0-9][a-z0-9-]{0,31}`。不再要求 `tunnel-` 前缀——那个前缀原本是为了
  跟系统用户区分开，现在账号根本不是系统用户。
- IP：IPv4 点分十进制，或方括号里的 IPv6。**不接受域名。**
- 校验：前面全部内容（到最后一个 `:` 之前）的 SHA-256 的前 4 个十六进制字符。
  它只防粘贴截断与手误，不是安全措施。
- 解析从右往左切（指纹与校验里都没有 `:`），再按最后一个 `@` 切账号。
- **连接码里没有秘密**：可以走普通渠道发，可以存在本机。口令单独发。

`account add` 的输出：

```
账号 tunnel-zhang 已开通，端口 22003。
连接码：  rmc1:tunnel-zhang@203.0.113.10:443:k3Jx…:9f2c
初始口令：XXXXXXXXXXXXXXXXXXXXXXXX      （只显示这一次）
远程工程师：ssh -p 22003 root@203.0.113.10
```

指纹从第一次连接起就是钉死的。客户端**没有**「首次连接自动信任」这条路，也不留作后备
——留了后备，钉死就形同虚设。这同时兑现了原方案 §7.3 里「固定 host key 列表并取消
首次连接信任」那一条。

## 5. 隧道

线上协议不变：TLS 里跑 SSH。

### 5.1 服务端只实现两件事

口令认证，与一条反向转发。除此之外的一切——公钥认证、`session` 通道（因而 shell、
exec、sftp、pty 全都无从谈起）、正向转发、agent 与 X11 转发——**不实现**，
russh 对未实现的回调默认就是拒绝。这是「让错的东西构造不出来」，
而不是靠配置去禁掉一个功能齐全的 sshd。

### 5.2 端口由服务端定

- 端口在开通账号时固定：取区间里最小的空闲号，或由 `--port` 指定（必须在区间内且未被占用）。
- 客户端申请端口 **0**，服务端把该账号的端口填回应答（RFC 4254 §7.1）。
  客户端申请了非 0 且不等于账号端口的，拒绝。
- 一个账号同一时刻只有一条隧道。
- 监听绑在 `0.0.0.0:<端口>`。工程师连进来 → 向客户端开一条 `forwarded-tcpip` 通道 →
  双向搬运字节。每条隧道最多 16 条并发的工程师连接。
- `--engineer-allow <CIDR>` 可以重复给；给了就只接受这些来源的工程师连接。
  **默认不设，即现状：反向端口公网可达**（原方案 §7.1 已明确接受的取舍）。

### 5.3 断开即回收

服务端每 10 秒发一次心跳，连续 3 次没有回应判定失联。隧道一断（TLS 连接关闭，或心跳失联），
**立即**关掉监听、断开它的全部工程师连接、释放端口。

同一个账号再次登录、而旧会话还没被判死：维持今天的语义——认证通过，申请转发时被拒
（端口占用），客户端按既有的 120 秒预算重试。等待时间从实测约 80 秒降到 30–40 秒。
（「探测旧会话、不应答就顶掉」能把这个等待变成零，记在 §10，这一轮不做。）

## 6. 原来由 sshd、PAM 与 haproxy 扛的，现在自己扛

| 项 | 做法 |
|---|---|
| 口令存储 | argon2id，PHC 字符串。初始口令由 bin 生成（18 字节随机，base64）；`passwd` 重置并只显示一次 |
| 账号存在性 | 账号不存在或已停用时**也跑一次等价的哈希**，失败应答的形状与耗时跟「口令错」一致 |
| 单连接 | 最多 3 次尝试；每次失败统一延迟 1 秒 |
| 按来源 IP | 10 分钟内失败 10 次 → 封 15 分钟。**不做按账号锁定**——那等于给了攻击者一个锁死合法账号的开关 |
| 未认证连接 | 从 TCP 建立到认证通过限 20 秒；未认证连接全局最多 64 条、每个 IP 最多 8 条 |
| 审计日志 | 认证成功与失败（账号、来源 IP）、隧道建立与拆除（原因）、工程师连接的起止（来源 IP、端口、时长、双向字节数）、账号的增删改。**这是原方案 §7.1 明确缺的那一块**；原方案里 sshd 看到的来源永远是 127.0.0.1，现在是真实地址 |

审计日志里**不写口令**，失败的认证只记账号名与来源。

## 7. 客户端改动

### 7.1 rmc-core

- `transport/tls`：公共 CA 校验整个去掉，换成 §4.1 的指纹核对；只开 TLS 1.3；
  删掉 `webpki-roots` 依赖。测试专用的「追加一个 PEM 根」随之消失。
- SSH host key：改成与同一个指纹比对。`known_hosts` 文件、首次记录、`Config::known_hosts_path`
  全部删掉。
- 反向转发：申请端口 0，读回端口，随隧道建立的事件带给上层。`Config::reverse_port` 与
  `ALLOWED_REVERSE_PORTS` 删掉。
- 新类型「连接码」：解析、校验、格式化，字段私有，构造不出不合法的值
  （同 `HostPort`、`Fingerprint` 的做法）。`Command::Start` 收连接码与口令，
  不再分别收运维服务器地址与账号。
- 预检四项改为：一体机 TCP、一体机 host key 指纹、运维服务器连通（直连或代理 CONNECT）、
  运维服务器 TLS 与指纹。「域名解析」那一项没有了。
- 指纹不一致归为**不重试**的失败，文案指出两种可能：路径上有 TLS 审计设备，
  或连接码已经过期（运维服务器换过密钥）。

### 7.2 rmc-app

- 维护页「运维服务器」一组：**连接码**（一个输入框，粘贴）、出网、密码、记住密码。
  连接码解析成功后，下面只读地显示解析出的地址与账号；解析失败，框下红字说明原因
  （格式不对、校验不符、不接受域名）。
- 已连接后显示「远程工程师请连接 `<IP>` 端口 `<N>`」。
- 连接成功过的连接码存在 `%LOCALAPPDATA%\rmc\connection-code.txt`，下次启动自动填好。
  它不含秘密，**存不存与「记住密码」无关**；`last-account.txt` 取消。
  「记住密码」的密文仍按「账号 + 地址 + 端口」定位。
- 诊断页：「运维服务器 host key」一行改成「运维服务器指纹」，显示「与连接码一致」或不一致。
- 界面用语规则不变：一律「运维服务器」，不出现 Gateway 与「网关」。新增用语「连接码」。

## 8. 测试与交付

- **进程内端到端。** rmc-core 的集成测试从 docker（haproxy + sshd + 模拟一体机）换成
  进程内的 rmc-gateway 服务端 + 进程内的假一体机（一个 russh 服务端）。
  这些测试不再是 `#[ignore]`，Linux 与 Windows 的 CI 都跑。
- **验收线：现有的客户端集成用例对着新服务端全绿**——正常建链与转发；口令错误后停止且
  不自动重试；指纹不符时拒绝连接且不重试；服务端断开后退避重连；端口占用重试；
  一体机不可达转 degraded 并在恢复后转回；HTTP CONNECT 代理路径；407 之后的 SSPI 协商；
  断线重连复用内存中的凭据。
- **服务端自己的用例**至少覆盖：§5.1 每一种被拒绝的请求；端口分配与回填；吊销在 10 秒内
  踢掉在线会话；§6 表里的每一行（含「账号不存在」与「口令错」不可区分）；
  隧道断开后端口立即可以重新绑定；CLI 并发改账号不丢更新；连接码的解析与校验。
- 变异测试的纪律照旧：每条关键测试写明「改哪一行会让它变红」，并且真的改一遍。
- **CI**：新增一个 job 产出 musl 静态二进制并上传；`cargo deny` 覆盖新依赖
  （预计新增 `argon2`、`rcgen`，CLI 解析与 CIDR 匹配尽量不引新包）。
  原来起 docker compose 的 `integration` job 随旧测试一起退役。
- **退役**：新服务端过了验收线之后，删除 `gateway/` 下的 haproxy 与 sshd 配置、systemd 单元、
  `registry.toml`、`scripts/`、`tests/`、`test-env/`。`gateway/README.md` 重写成新 bin 的
  部署手册（目标：一页）。
- **文档**：`docs/方案设计.md` 第 2、3（传输、本地存储、界面）、4、6、7、8、9、12 章同步改，
  第 11 章加一行「haproxy + sshd-tunnel（V1 原方案）」并写明被替换的原因；
  `docs/使用手册.md`、`docs/windows-验收清单.md`、`docs/交付前还剩什么.md`
  （第 5、6 条随之关闭）同步改。

## 9. 代价与风险

- **安全责任转移到我们身上。** OpenSSH 与 haproxy 久经审计，客户的安全团队认识它们；
  现在口令存储、防爆破、连接限额、SSH 服务端的协议实现与补丁节奏都是我们的。
  russh 的服务端远不如 OpenSSH 久经考验。缓解：实现面极小（§5.1）；认证仍在 SSH 体系内
  （当初否掉 frp 的那条理由在这里不成立）；russh 本来就是客户端的依赖，
  `cargo deny` 已经在盯它的安全公告。
- **裸 IP。** 个别企业代理按策略拒绝 `CONNECT` 到 IP 地址。遇到只能请客户网管放行
  这个 IP 的 443。没有 SNI 的 TLS 在少数检测设备眼里也更可疑。这是「只用 IP」的已知代价。
- **指纹分发全靠连接码。** 连接码被人调包（把现场人员引向一台假服务器）就能收走隧道口令，
  所以连接码虽然不含秘密，仍应当经可信渠道交付。拿到隧道口令的人到不了一体机——
  那还需要动态 root 口令。
- **身份密钥丢失**＝所有现场笔记本都要重新拿连接码。备份数据目录。

## 10. 记账不做

探测旧会话、不应答就顶掉（把端口占用的等待变成零）；口令自助修改；
按来源限速之外的更细的配额；审计日志外发；aarch64 发布物；
`docs/交付前还剩什么.md` 里与服务器无关的各条不受本设计影响。
