# 交付前还剩什么

`rmc-win` 与 `rmc-app` 十二个任务做完、CI 五个 job 全绿、已并入 `main`
（`3f81090`）之后，**还没做的事**都在这里。执行方针是「先完成，再完善」，
这张表就是「再完善」那一半的输入。

分三档。分档的判据不是严重度，是**成本会不会随时间涨**（账本 W124）：

- **A** — 会在现场造成实际损害；
- **B** — 功能缺口：方案要求过，但没做完；
- **C** — 记账不修：今天修和半年后修一样贵。

编号沿用 Task 12 交付时的原表（根 `Cargo.toml` 的注释按编号引用过它），
已关掉的条目**留着不删**，只标注是被什么关掉的。出处里的 `W…` 指
`docs/superpowers/ledgers/2026-09-13-rmc-win-and-app.md` 里的裁决编号；
「Task N 报告」是执行期的过程文件，**没有入库**，对应的结论在那份账本里

## 自动化够不着的地方

CI 全绿不等于这些被验过。**它们只能靠 `docs/windows-验收清单.md` 在真机上人工走。**

- **`#[cfg(windows)]` 那几层 Win32 封装一条测试都没有**：DPAPI、托盘、电源事件、
  WinHTTP 代理发现、SSPI 协商、单实例互斥。`windows-build` 跑的 407 条全是
  纯逻辑层——它验的是同一批逻辑在 Windows 的 std 与文件系统语义下成不成立，
  不是这几层。
- **`main()` 的接线**：`assemble()` 以下有测试（W177），`main()` 自己没有。
- **Consolas 在真 Windows 上解析不解析得到**：`monospace_family` 的选择有测试，
  字体真的画出来只有真机看得见（W179）。
- **两个 tokio runtime 并存**（iced 的与内核的）：第一次真跑要留意（W113）。
